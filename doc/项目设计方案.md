关键决策说明：

framework-web 合并原 framework.spring + framework.tomcat。原因：DispatcherServlet 继承 HttpServlet，Request 实现 HttpServletRequest 又要返回 MultipartResolver，Catalina 又引用 DispatcherServlet，SpringApplication 又引用 Catalina——原 core 和 tomcat 双向耦合，强行拆会引入 framework-servlet-api 这类中间层，代价大。合并成 framework-web 是最务实的。

framework-web 依赖 framework-mybatis。因为 AnnotationConfigApplicationContext.registerMappers() 直接用 MapperProxy 和 JdbcTemplate。如果想彻底解耦，后续可改成 BeanPostProcessor 由业务模块注册，但拆分阶段不做这个重构。

omni-common-log 必须最先下沉，因为 common.cache、common.util 都依赖日志。

business 按 6 个领域聚合，不按 16 个目录硬拆。

十五、最关键的三条纪律
包名不改，只搬物理目录。 唯一例外：ConfigLoader 重命名、PlaywrightStealthUtil 改包名、ParamUtils/DataModelConverter/DriverLoader/DynamicDataSourceManager 上移。这些都要全局 grep + sed 替换。

依赖方向严格单向：common → framework → business → bootstrap。 每加一个依赖前问自己：会不会反向？SpringApplication → ScreenshotAssistantBootstrap 就是典型反向依赖，必须用反射或移到 bootstrap 解决。

每阶段 mvn install + 启动冒烟。 不要等全部搬完再启动，否则定位问题成本极高。

十六、一句话总结
先建 omni-parent 骨架并用空模块验证构建；然后按 common-log → common-core → common-config/cache/excel → framework-jdbc → framework-mybatis → framework-web → 其余 framework → business 6 个聚合模块 → bootstrap 的顺序逐步搬迁，每步 mvn -pl ... -am install 并冒烟；包名保持不变，只处理 ConfigLoader 重命名、PlaywrightStealthUtil 改包、DynamicDataSourceManager/DriverLoader/ParamUtils/DataModelConverter 上移、SpringApplication 对 ScreenshotAssistantBootstrap 的反向依赖这 5 个关键重构点。
